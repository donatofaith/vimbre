# Account and company setup

## Implemented flow

Signup collects full name, company name, work email and a matching password of 12–128 characters. Supabase Auth stores the credentials. An auth.users insert trigger atomically creates a company and a profile with the HR Admin role. Only the two display names are read from user metadata; role and company identifiers are generated by trusted database code. Employee invitations use the separate controlled flow in team-setup.md, not this company signup endpoint.

Confirmation links return to /auth/callback. The SDK exchanges PKCE codes and the provider verifies the user with Auth before loading the active profile and company. /app and nested routes require that verified account. Session persistence and refresh use the Supabase SDK. Auth event handlers never await another Auth request inside the callback.

Forgot password gives a generic response and sends a recovery redirect to /auth/callback?flow=recovery. The reset form requires a valid session, updates the password through Auth and signs out. Open confirmation and recovery links in the browser that requested them because PKCE stores the verifier locally. Missing, invalid and expired links show recovery instructions.

HR Admins can edit company name, contact email and small/departments team mode. Manager and Employee accounts see read-only company settings. Department management and invitations are now implemented; see team-setup.md.

4. Preserve Supabase's confirmation and recovery link semantics in email templates. PKCE confirmation and reset links must reach the app callback.
5. Test with an inbox owned by the project team: signup, received email, confirmation, login, reload, logout, recovery email, new password and old-password rejection. Test expired and reused links. Do not treat a successful SDK response as proof of email delivery.
6. Before production, use a separate project, apply these migrations in order, supply its URL/publishable key and repeat isolation and email acceptance tests.

## Database boundary

Public tables: companies, departments, profiles and activity_log. Every table has RLS. A membership's company, role and department come from the protected profile, not editable JWT user_metadata. Authenticated clients receive only necessary table/column grants. They cannot create profiles/companies directly, change roles/company membership, write departments or forge audit records.

Private SECURITY DEFINER helpers avoid recursive profile policies and look up only auth.uid(). They use an empty search path and restricted execution. Trigger functions are not client callable. The platform-installed rls_auto_enable DDL handler also has client execution revoked.

Schema migration versions match the development project's recorded versions. Changes to applied migrations must be follow-up migrations, not rewritten history. Regenerate src/lib/database.types.ts after schema changes.
